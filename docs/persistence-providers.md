# Persistence: what differs between PostgreSQL and SQL Server

The domain does not know which engine it runs on, and neither do the repositories, the entity
configurations or the outbox. Everything engine-specific is either behind `IPersistenceProvider` or
in a per-engine DbUp script folder.

This document records what was found to genuinely differ, and why each difference was worth
respecting rather than flattening into a lowest common denominator.

## 1. Optimistic concurrency

| | PostgreSQL | SQL Server |
|---|---|---|
| Mechanism | hidden `xmin` system column | explicit `rowversion` column |
| CLR type | `uint` | `byte[]` |
| Configuration | `Property<uint>("Version").IsRowVersion()` | `Property<byte[]>("RowVersion").IsRowVersion()` |
| Schema cost | none | one column per table |

The differing CLR type is the whole reason `IPersistenceProvider.ConfigureConcurrencyToken` exists:
no single shared line can configure both.

`UseXminAsConcurrencyToken` is **not** used. It was obsoleted in version 7.0 of the Npgsql EF Core
provider, which made concurrency tokens configurable through the standard EF API instead.

Both are mapped as **shadow properties**. Concurrency is a persistence concern, and an aggregate
carrying a `Version` member would expose the storage engine's bookkeeping as part of its business
API.

One caveat on `xmin`: its values are not preserved across `pg_dump` / `pg_restore`. Harmless here,
where a token lives for the duration of one request, but it rules out handing the value to a client
that keeps it for days.

## 2. GUID ordering — the difference that costs the most

All identifiers are UUIDv7: time-ordered, so keys are generated by the application yet still land in
insertion order in an index.

That holds on PostgreSQL. It does **not** hold on SQL Server.

```
UUIDv7 byte layout        [ timestamp ][ random ]
                            bytes 0-5    6-15

PostgreSQL uuid order     bytes 0 → 15          timestamp is most significant  → sequential
SQL Server uniqueidentifier
                          bytes 10-15, 8-9,
                          6-7, 4-5, 0-3        timestamp is LEAST significant → random
```

A stream of UUIDv7 values therefore arrives at random positions in a SQL Server clustered index and
splits pages on nearly every insert.

The schema handles this rather than the application, because changing the identifier scheme would
mean giving up a property PostgreSQL gets for free:

```sql
-- every table, SQL Server only
CONSTRAINT pk_document PRIMARY KEY NONCLUSTERED (id);
CREATE CLUSTERED INDEX ix_document_clustered ON document (created_at, id);
```

Inserts append to the clustered index, and lookups by id still use the primary key. PostgreSQL has no
clustered indexes at all, so its scripts carry none of this.

The table where it matters most is `outbox_message`: highest insert rate in the system, clustered on
`occurred_at`.

## 3. Claiming outbox messages

Both engines can skip rows another transaction holds instead of blocking on them — the property that
lets several dispatchers run without a distributed lock.

```sql
-- PostgreSQL
FOR UPDATE SKIP LOCKED

-- SQL Server
FROM outbox_message WITH (UPDLOCK, READPAST, ROWLOCK)
```

All three SQL Server hints are required. `READPAST` alone skips locked rows but takes no lock of its
own, so two workers claim the same message; `ROWLOCK` stops the engine escalating to a page lock and
stealing rows a sibling would have taken.

## 4. Recursive queries

The folder ancestry walk is the same algorithm with incompatible syntax:

| | PostgreSQL | SQL Server |
|---|---|---|
| Keyword | `WITH RECURSIVE` required | `WITH` — `RECURSIVE` is rejected |
| Depth guard | predicate only | predicate plus `OPTION (MAXRECURSION 64)` |

The depth predicate is not decoration on either side. A cycle introduced by a faulty migration would
otherwise recurse until the connection dies, and a hung connection is a worse failure than a
rejected request.

## 5. Expression indexes

Sibling name uniqueness needs a normalised key: parent plus lower-cased name.

```sql
-- PostgreSQL indexes the expression directly
CREATE UNIQUE INDEX ux_folder_sibling_name
    ON folder (COALESCE(parent_id, '0000...'::uuid), lower(name))
    WHERE deleted_at IS NULL;

-- SQL Server cannot index an expression, so it is materialised first
ALTER TABLE folder ADD sibling_key AS (...) PERSISTED;
CREATE UNIQUE INDEX ux_folder_sibling_name ON folder (sibling_key) WHERE deleted_at IS NULL;
```

Both are filtered on `deleted_at IS NULL`, which both engines support.

## 6. Smaller differences

| Concern | PostgreSQL | SQL Server |
|---|---|---|
| Instant | `timestamptz` | `datetimeoffset(7)` |
| Outbox payload | `jsonb` | `nvarchar(max)` |
| Digest column | `varchar(64)` | `varchar(64)` — never `nvarchar` |
| Text | `varchar` | `nvarchar` |
| Id array parameter | `= ANY(@Ids)` | `IN @Ids`, expanded by Dapper |
| Deferrable FK | used for `document → current_version` | unavailable; the aggregate enforces it |

`varchar(64)` for the SHA-256 digest on both engines is deliberate. `nvarchar` would double the size
of every key, every index entry and every foreign key pointing at it, for a character set the value
can never contain.

The deferrable foreign key is the one guarantee PostgreSQL has and SQL Server does not: a document
and its first version are inserted in the same transaction and neither can legally be written first.
PostgreSQL defers the check to commit; on SQL Server the constraint is simply absent, and the
invariant rests on the aggregate never exposing a way to point `CurrentVersionId` at a version it
does not own.
